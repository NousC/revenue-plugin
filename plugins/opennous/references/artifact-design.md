# Artifact design system — branded reports

Some skills render a **branded HTML artifact** after they write their markdown. This file is the
design system and the rules so every artifact looks like one family. Start from
**`artifact-template.html`** (the reference skeleton, already filled with a real example) and swap in
the report's content — never hand-roll new CSS per report.

> This is a **foundation, in progress.** Keep the shell, tokens, and rules; refine the details over time.

**The principle: consistent shell + rules, unique body.** Every artifact wears the same design, chrome,
linking, citations, and language rules — that is the consistency. Each skill fills its own sections,
prose, and visuals — that is the uniqueness. Never clone one skill's section list onto another.

## When to make an artifact
Only these skills, and only when the output is **(1) shared or presented AND (2) visual**:
**`onboard` / `revenue-report` (the Revenue Report) · `review-pipeline` · `map-committee`.**
Every other skill outputs plain markdown/text. Never render an artifact for a conversational answer,
an action draft, or read-once working material. When unsure, text is the right default.

## Host + flow
- **Claude Code only** — it renders self-contained HTML. Other hosts (Codex, Claude Desktop) get the
  markdown, or their own native treatment later.
- **Markdown is the source of truth; the artifact is a presentation layer on top.** Write the markdown
  report first, then render this template with the *same* content, then publish the artifact.
- **Self-contained:** inline CSS + inline SVG only. No external fonts, images, scripts, or CSS — the
  artifact CSP blocks them, and a linked webfont fails silently.

## The look (fixed — copy from the template, vary only the content)
- **Ground:** warm cream paper `#f5f1ea` with a faint gradient at the bottom. Sections and the table
  sit **on the paper** — no white cards floating on cream.
- **Type — three roles:**
  - **serif** (`Charter`, `Iowan Old Style`, Palatino, Georgia) for the reading body,
  - **sans** (`system-ui`) for headings, the "generated for" line, section sub-descriptions, the stats
    band, the table, and captions,
  - **mono** (`Geist Mono`, `JetBrains Mono`) for numbers, dates, and source refs.
  One body size throughout — **no oversized lead paragraph.**
- **Color hierarchy (consistent):** head `#211f1b` · body `#38332c` · soft `#6d675e` · faint `#948d82`.
  Accent orange `#e85b3d` used **sparingly** (source-ref marks, the one hero highlight, viz dots).
  Logo nucleus `#ff5c00`.
- **Logo:** the atom mark (inline SVG in the template) + `OpenNous`, top-left; a small version in the
  footer.

## The shell is fixed; the body is the skill's own
**Every artifact shares the same shell and rules — that is what makes them one family. What each
artifact says inside is unique to the skill.** Do not force one skill's sections onto another.

**Fixed across every artifact (never varies):**
- The masthead — atom logo + `OpenNous`, top-left.
- The title (`h1`, sentence case) + **one line only**: `Generated for {person}, {company}.` Nothing
  else under the title (no date/scope line, no sub-description).
- The **source-citation footnotes** and the **footer** (`generated by {logo} OpenNous · {date}`).
- Everything in **The look**, **Linking**, and **Language rules** below.

**Unique to each skill (its own body, between title and sources):**
- The sections, their `h2` titles, the prose and bullets, the stats band, and the visuals. A pipeline
  review, a forecast, a revenue report, and a committee map answer different questions, so their
  sections and charts are their own. Choose the sections and the one or two visuals that actually
  serve *this* skill's job, and write them to the shared rules.

**Order:** masthead → title + generated-for → the skill's body → sources → footer.
A stats band and minimal inline visuals are available (see the template) — use them where they earn
their place in that skill, not by rote.

## Personalization is the point
- Personalize the **content** to the customer: the `Generated for {name}, {company}` line and their
  real accounts, people, numbers, and quotes throughout.
- The **design stays OpenNous** (logo, palette, footer). It is *their* report, generated by OpenNous.

## Linking — every account and person is a live link into the app
Whenever you name an account/company or a person, in the table AND in prose, link it to its record in
the app so the reader can click straight through:
- company/account → `https://app.opennous.cloud/accounts/<entity_uuid>`
- person → `https://app.opennous.cloud/people/<entity_uuid>`

Use the **full entity UUID** from the graph — `get_account` and `query` return each entity's `id`
(e.g. `143c8ce5-b8ba-4a95-b908-bc4f897593b7`). **Never truncate it or invent one**; a shortened or
made-up id opens the wrong record or 404s. Style the links with the `.lnk` class from the template
(hairline underline, orange on hover). Link the first mention in prose, and every name in the table.

## Trust — cite every non-obvious fact
- Any specific claim (a number, a quote, a commitment, a buying signal) carries a **footnote marker**
  that links to a **Sources** list at the bottom.
- Each source **links to the exact raw transcript in the user's git** (a GitHub URL into their
  `nous-raw` repo, the file the claim came from). Every number traces back to the sentence a customer
  actually said. This is the trust layer, in the report.

## Language rules (non-negotiable — see also `language.md`)
- **Sentence case everywhere.** Never uppercase headings or labels. Never eyebrows.
- **Never a `—` (em dash) or a `:` (colon) inside a sentence.** Rewrite with periods and commas.
- **No bold inside paragraphs.**
- **Numerals, not words:** `12 calls`, not "twelve".
- **Mix prose and bullets:** prose for narrative (exec, patterns, coverage); bullets for discrete
  lists (the reveal, the market signals). Don't force everything into one mode.
- **No decorative section-number markers** (01/02) unless the content is a genuine sequence.

## Rule number one: make it valuable — depth over surface
A thin report is a failed report. Every section must deliver real substance — named accounts, exact
numbers, real quotes, the specific commitment or signal, and the decision it surfaces. And go past the
fact to the **why**: what caused it, what it means, what is behind it. "You have a network, not a
pipeline" is surface; "you build inside an operator circle, so the graph reflects who you talk to
rather than who buys" is the insight. Every point should explain itself. Depth earns trust; padding and
surface-level summary kill it. If a section only states what happened, it is not finished.

## Visuals — minimal but useful
Add a visual only when it explains something better than prose can (a distribution, a coverage split,
a funnel). Inline SVG, on-brand (orange marks on grey), with a one-line caption that states the
insight. Keep them few and quiet — a report is not a dashboard.

## Publishing
Render the template filled with the real content (self-contained), then publish it as the artifact.
The document saved to Pages (`save_page`) is the source of truth; the artifact is the shareable layer.
